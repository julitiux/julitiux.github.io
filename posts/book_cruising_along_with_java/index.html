Implementing interfaces

Records, being classes, are permitted to implement interfaces. What interfaces a record may implement is of course domain- and application-dependent. It may be hard to imagine why a record would implement interfaces like Runnable o Callable. But it’s conceivable that a record could implemnt interfaces that may provide consistency in data handling.

public interface Json {
  String generateJson();
}

We can easily evolve the Location record to implement the json interface

public record Location(double latitude, double longitude) implements Json {
  @Override
  public String generateJson() {
    return """
    {
      "latitude": %g,
      "longitude": %g
    }
    """.formatted(latitude, longitude);
  }
}

Considering a Custom Canonical Constructor?

Java allows you to create a canonical constructor for Recordsm but also provides a newer compact constructor.

public record Location(double latitude, double longitud) {
  public Location(double latitude, double longitude) { //not preferrable
    if(latitude < -90 || latitude > 90 || longitude < -180 || longitude > 180 ){
        throw new RuntimeException("The location is out of this world");
    }

    this.latitude = Math.round(latitude * 100.0) / 100.0;
    this.longitude = longitude;
  }
}

Preferring the Compact Constructor

Think of the constructor more like a preprocessor than a constructor. Use the compact constructor to validate, transform, and/or cleanse datam and leave the initialization of the fields to the autogenerated canonical constructor.

public record Location(double latitude, double longitude) {
  public Location {
    if(latitude < -90 || latitude > 90 || longitude < -180 || longitude > 180 ){
      throw new RuntimeException("The location is out of this world");
    }
  latitude = Math.round(latitude * 100.0) / 100.0;
  }
}

This makes the code more extensible and honors the Open-Closed Principle. Let’s recap what we’ve done. You may write a compact constructor or a custom canonical constructor, but not both. If you only want to initialize fields and have no need to validate of transform datam then don’t write either the compact constructor or the canonical constructor. The default constructor provided is adequate in this case. But if you need to write one, then write the compact constructor instead of the custom canonical constructor, as that’s simplre, less verbose, less error-prone, and simply looks cool compared to the all-too-familiar constructor.

Designing with Sealed Classes and Interfaces

To facilitate such requirements Java has evolved to include sealed classes and sealed interfaces. An interface or a class marked as sealed clearly specifies what can be implemented or extended from it. This provided a way to close the hierarchy with only the desired memebers. Any attempt to extend the hierarchy further will result in a compilation error.

Need for a Closed Hierarchy

Like seaed classes, enums also provide the capability to create a closed hierarchy. “Should we choose an enum or sealed classes?” is a reasonable question.

Prefer enum if you’re designing a closed set og fixed predetermined constants, like the JDK’s DayOfWeek enum. The values that are part of an enum share the same properties and methods.

To close the hierarchy of classes that aren’t part of a fixed set of constants use sealed. Unlike enums, sealed classes that are part of a closed hierarchy may have different methods and properties. You also have the flexibility to extend the hierarchy to multitple levels.
